1. Introduction                                       *gh-review-introduction*

gh-review.nvim is a Neovim 0.10+ plugin for reviewing GitHub pull requests.
It provides side-by-side diffs, review thread viewing and commenting, commit
suggestions, and review submission — all driven by the `gh` CLI.

The goal of this plugin is to provide the simplest means possible for
performing GitHub PR reviews.  It is designed for the use case where you
have already identified a specific PR or PR branch you are ready to review.
Anything beyond that is a non-goal — for example, GitHub Issues,
Notifications, Discussions, Actions, PR listing, or label/assignee/reviewer
management.  You are expected to perform those tasks using other tooling.

==============================================================================
2. Requirements                                       *gh-review-requirements*

- Neovim 0.10 or later
- `gh` CLI (https://cli.github.com), authenticated
- A git repository with a GitHub remote

==============================================================================
3. Workflows                                             *gh-review-workflows*

The plugin has two main workflows.

CHECKOUT WORKFLOW ~
                                                  *gh-review-checkout-workflow*

The checkout workflow is typically used by a project maintainer reviewing a
contributor’s PR.  The branch is checked out locally so the reviewer can
make edits, commit fixes, and push directly.

Use |:GHReview| with no argument (auto-detects the PR from the current
branch), a PR number, or a URL that refers to the same repo as the current
working directory.

- If the current branch already matches the PR’s head ref, the plugin
  skips the checkout prompt and loads the UI immediately.
- Otherwise, the plugin prompts to check out the branch.  On confirmation,
  the branch is fetched and checked out, and push tracking is configured
  automatically (for both same-repo and fork PRs).
- The right/head diff buffer is editable: |:w| writes to the working tree.
  External file changes (e.g., from another editor or `git stash pop`) are
  detected via mtime tracking, and the plugin prompts to reload.
- `git push` pushes changes back to the PR branch with no extra flags.

If you decline the checkout, or the checkout fails (e.g., dirty working
tree), the plugin falls back to the no-checkout workflow.

NO-CHECKOUT WORKFLOW ~
                                               *gh-review-no-checkout-workflow*

The no-checkout workflow is more typical of a non-maintainer reviewer who only
needs to read the diff and leave comments.

Use |:GHReview| with a URL that refers to a different repo than the current
working directory.  This workflow also activates as a fallback when a checkout
is declined or fails.

- No checkout is offered or attempted.
- Diff content is fetched via the GitHub API.
- The right/head diff buffer is read-only.
- Comments, suggestions, and review submission all work normally.

A quick-start sequence for either workflow: >

    :GHReview 123           Open PR #123 (or :GHReview {url})
    <CR>                    Open a file’s side-by-side diff
    ]t / [t                 Jump between review threads
    gt                      View a thread
    gc                      Add a comment
    gF                      Jump to the file with LSP (checkout only)
    :GHReviewStart          Start a pending review (optional)
    :GHReviewSubmit         Submit the review
    :GHReviewClose          Close all review buffers
<

4. Commands                                               *gh-review-commands*

                                                                   *:GHReview*
:GHReview               With no argument, detect the PR from the current
                        branch via `gh pr view`.

:GHReview {number}      Open a pull request by number, in the clone’s base
                        repo: the remote that `gh repo set-default` chose,
                        if any; otherwise `upstream`, `github`, or `origin`,
                        in that order.  That’s the repo `gh pr view` uses —
                        so in a clone of a fork, it’s the parent repo.

:GHReview {url}         Open a pull request by URL, on github.com or on a
                        GitHub Enterprise host.  If one of the clone’s
                        remotes points at the URL’s repo, the checkout
                        workflow is used; otherwise the no-checkout workflow.

                        With a PR number or no argument, API requests go to
                        the host of the base repo.

                        See |gh-review-workflows| for details on when the
                        branch is checked out and when it is not.

                                                              *:GHReviewFiles*
:GHReviewFiles          Toggle the changed files list buffer.

                                                              *:GHReviewStart*
:GHReviewStart          Start a pending review.  All subsequent comments will
                        be held as pending until the review is submitted.
                        This is optional; |:GHReviewSubmit| works without it.
                        If a pending review already exists on the PR (from a
                        previous session or the GitHub web UI), it is detected
                        automatically and reused.

                                                             *:GHReviewSubmit*
:GHReviewSubmit         Submit a review.  Prompts for the review action
                        (Comment, Approve, or Request changes) and an optional
                        body.  If a pending review is active, it is submitted;
                        otherwise a review is created and submitted in one
                        step.

                                                            *:GHReviewDiscard*
:GHReviewDiscard        Discard the pending review.  Prompts for confirmation,
                        then deletes the review and all its pending comments.

                                                               *:GHReviewHelp*
:GHReviewHelp           Show every configured key and command in a float
                        (also `?` in the files list, `g?` in the diff and
                        the comment buffer).

PR DRAFTS ~
                                                         *gh-review-drafts*

On a PR, `:w` / <C-s> in the comment buffer saves the comment or reply as a
draft on this machine (`stdpath("data")/gh-review/drafts/`), not on GitHub.
|:GHReviewSubmit| publishes all drafts as one review (Comment, Approve,
Request changes) or uploads them to a pending review without publishing.
|:GHReviewDiscard| deletes them.  `pr_drafts = false` posts each comment when
written instead.

                                                              *:GHReviewClose*
:GHReviewClose          Close all review buffers and reset plugin state.

:GHReview branch [{base}]
:GHReview uncommitted
:GHReview turn          Open a local scope, with no PR.  See
                        |gh-review-scopes|.

                                                              *:GHReviewScope*
:GHReviewScope {scope} [{arg}]
                        Switch the open review to {scope}: `pr`, `branch`,
                        `uncommitted`, or `turn`.  `branch` takes a base,
                        `pr` a number or URL.  The open file stays open when
                        the new scope has it.

                                                               *:GHReviewSend*
:GHReviewSend           Paste the comments into a running coding agent.  In
                        a local scope: unsent comments, which are then marked
                        sent.  In PR scope: every unresolved thread, left as
                        it is on GitHub.  See |gh-review-agent|.

                                                               *:GHReviewCopy*
:GHReviewCopy           Copy the text |:GHReviewSend| would send.

                                                               *:GHReviewTurn*
:GHReviewTurn           Mark the last-turn baseline now: snapshot the working
                        tree, untracked files included.

5. Diff View                                             *gh-review-diff-view*

The diff view shows two vertically split buffers in Neovim’s native diff mode:
the left buffer shows the base version (at the merge base commit) and the
right buffer shows the head version (at the PR’s head commit).

In the checkout workflow, the right buffer is editable.  |:w| writes to the
working tree, and external file changes are detected automatically.  If the
file changes on disk (e.g., from another editor), the plugin prompts to
reload.

In the no-checkout workflow, the right buffer is read-only.

Both diff windows display a winbar showing the PR number, file path,
side (base/head), and a short commit OID for persistent context.

DIFF MAPPINGS ~
                                                    *gh-review-diff-mappings*

gt                      Open the review thread at the cursor line.
gc                      Create a new comment at the cursor line.
                        In visual mode, creates a multi-line comment.
gs                      Create a suggestion at the cursor line (right buffer
                        only).  In visual mode, creates a multi-line
                        suggestion.
]t                      Jump to the next review thread sign.
[t                      Jump to the previous review thread sign.
K                       Preview the thread at the cursor line in a floating
                        window.  Lighter than `gt` — no split, no reply
                        area.  Close with `q`, `<Esc>`, or |BufLeave|.
gf                      Toggle the files list.
gF                      Go to the file at the cursor line (checkout workflow
                        only, right buffer only).  Closes the diff view and
                        opens the working-tree file with full LSP support.
q                       Close the diff view, returning to the files list.

==============================================================================
6. Signs and Virtual Text                                  *gh-review-signs*

Review threads are indicated by extmarks in the sign column of diff buffers:

CT                      Comment thread (blue).  The most recent comment has
                        state COMMENTED.
CR                      Resolved thread (green).
CP                      Pending thread (yellow).  The thread contains a
                        comment from the current pending review.

Each sign is accompanied by virtual text at end-of-line showing the first
comment’s author and a truncated body (up to 60 characters),
highlighted with `GHReviewVirtText`.  This gives at-a-glance context without
opening the thread.

REACTIONS ~
                                                      *gh-review-reactions*

Comment reactions are displayed after each comment body in both the thread
buffer and the floating preview (`K`).  Reactions appear as emoji with
counts, for example:

  👍 3  🎉 1

Reactions are read-only — the plugin does not provide a way to add or
remove reactions.

Signs are placed on the appropriate side (left or right buffer) depending on
the thread’s diff side.  For outdated threads where the line number is no
longer valid, the sign falls back to the original line number.

Use `]t` and `[t` to jump between signs.  Use `K` to preview a thread in a
floating window.

Highlight groups (all set with `default = true`, so user overrides take
precedence):

`GHReviewThread`          Sign column text for normal threads.
`GHReviewThreadResolved`  Sign column text for resolved threads.
`GHReviewThreadPending`   Sign column text for pending threads.
`GHReviewVirtText`        Virtual text showing comment previews.

==============================================================================
7. Thread Buffer                                     *gh-review-thread-buffer*

The thread buffer opens in a bottom split showing the thread’s code context,
comments, and a reply area: >

    Thread on src/main.rs:42  [Active]
    ----------------------------------------------------------------
      42 + | let x = foo();
    ----------------------------------------------------------------

    alice (2025-01-15):
      Looks good

    -- Reply below (Ctrl-S to submit, Ctrl-R to resolve, Ctrl-Q to cancel) --

<
The area above the separator is read-only.  The area below is the reply
editor.

THREAD MAPPINGS ~
                                                  *gh-review-thread-mappings*

CTRL-S                  Submit the reply text (below the separator line).
CTRL-R                  Resolve or unresolve the thread.
q                       Close the thread buffer.
CTRL-Q                  Close the thread buffer (works in insert mode too).

The thread buffer uses |’buftype’| `acwrite`, so |:w| also submits the reply.

@-MENTION COMPLETION ~
                                              *gh-review-thread-completion*

The thread buffer sets |’omnifunc’| to a function that completes
`@`-mentions from thread participants.  Trigger with CTRL-X CTRL-O in
insert mode.  The completion list includes all unique comment authors
across all review threads.

==============================================================================
8. Files List                                           *gh-review-files-list*

The files list opens in a bottom split showing changed files with their
diff stats and thread counts: >

    https://github.com/owner/repo/pull/123: Fix the widget
    Files changed (3)

      +12 -3   M  src/main.rs         [2 threads]
      +45 -0   A  src/new_file.rs
      +0  -22  D  src/old_file.rs
<
Mappings:

<CR>                    Open side-by-side diff for the file under cursor.
<Space>                 Toggle the reviewed state of the file under cursor.
q                       Close the files list.
gf                      Close the files list (same as q).
R                       Refresh review threads from GitHub.  In a local
                        scope, re-read the files from git and the comments
                        from the store.
S                       Send comments to a coding agent (|:GHReviewSend|).
p b u t                 Scope: PR, branch, uncommitted, last turn.
s                       Toggle the stack view (|gh-review-stack|).
<Tab>                   Stack view: fold or unfold the frame under the
                        cursor and what it calls.  Every level folds, so
                        |zM| and |zr| collapse or open a level across all
                        stacks; folds survive redraws.  The fold column
                        shows ▾ (open) and ▸ (folded); a folded frame
                        keeps its line and adds "··· N frames".
P                       Move the list between the bottom and the left.
?                       Show every key (files list, diff, comment buffer)
                        and command, as configured, in a float.  q, <Esc>,
                        or ? closes it.

9. Statusline                                          *gh-review-statusline*

The plugin provides a statusline component for integration with statusline
plugins (lualine, heirline, etc.): >lua

    require("gh_review").statusline()
<
Returns an empty string when no review is active, or a summary like
`PR #42 · reviewing · 4 threads`.

Example with lualine: >lua

    require("lualine").setup({
      sections = {
        lualine_x = { require("gh_review").statusline },
      },
    })
<

10. vim.ui Integration                                    *gh-review-vim-ui*

All user prompts (submit review action, review body, discard confirmation,
checkout confirmation, external file change reload) use |vim.ui.select()|
and |vim.ui.input()| instead of legacy |inputlist()| / |input()|.

Plugins like dressing.nvim or fzf-lua that override `vim.ui` hooks will
automatically provide their enhanced UIs for these prompts.

All keymaps include `desc` fields, making them discoverable via which-key.nvim
and |:map|.

11. Configuration                                          *gh-review-config*

Calling setup() is optional.  Commands register automatically without it.
Call it only to change keymaps or folding: >lua

    require("gh_review").setup({
      keymaps = {
        diff  = { preview = false },
        files = { toggle_viewed = "v" },
      },
      fold = { level = 99 },
    })
<
Only the keys you write are changed; everything else keeps its default.

An unrecognized surface, action, or value type is reported through
|vim.notify()| and the whole setup() call is ignored, so a typo fails
loudly rather than half-applying.

KEYMAPS ~
                                                          *gh-review-keymaps*

A mapping is either a string, which remaps it, or `false`, which drops it.
Dropping is how you free `K` for |K| / LSP hover, or `<Space>` for your
leader key.

Defaults, by surface: >lua

    diff = {
      thread_open  = "gt",
      comment      = "gc",
      suggestion   = "gs",
      next_thread  = "]t",
      prev_thread  = "[t",
      preview      = "K",
      toggle_files = "gf",
      goto_file    = "gF",
      to_stack     = "gS",
      close        = "q",
      send              = false,
      scope_pr          = false,
      scope_branch      = false,
      scope_uncommitted = false,
      scope_turn        = false,
      next_frame        = "]s",
      prev_frame        = "[s",
      help              = "g?",
      toggle_view       = "gu",
      next_hunk         = "]c",
      prev_hunk         = "[c",
    },
    files = {
      open          = "<CR>",
      toggle_viewed = "<Space>",
      refresh       = "R",
      toggle_files  = "gf",
      close         = "q",
      send              = "S",
      scope_pr          = "p",
      scope_branch      = "b",
      scope_uncommitted = "u",
      scope_turn        = "t",
      toggle_stack      = "s",
      toggle_fold       = "<Tab>",
      toggle_position   = "P",
      help              = "?",
      toggle_view       = "gu",
    },
    thread = {
      submit       = "<C-s>",
      resolve      = "<C-r>",
      close        = "q",
      close_insert = "<C-q>",
      help         = "g?",
    },
<
`comment` and `suggestion` each bind both normal and visual mode.  `submit`
and `close_insert` each bind both normal and insert mode.  You configure one
key and every mode for it follows.

The reply hint in the thread buffer names whichever keys you configured, and
omits any action you disabled.

FOLDING ~
                                                             *gh-review-fold*

    fold = { enabled = true, level = 0 }    Default: diff folds, all closed.
    fold = { enabled = true, level = 99 }   Diff folds, all open on arrival.
    fold = false                            No fold management at all.

`fold = false` is shorthand for `fold = { enabled = false }`.

|:diffthis| sets 'foldmethod' to "diff" by itself, so disabling folding means
the plugin actively sets 'nofoldenable' once.  After that it leaves folding
alone entirely, including declining to restore 'foldmethod' when another
plugin changes it.  In the other two modes it does restore it, at whatever
fold level you configured.

TURN ~
                                                         *gh-review-turn-opts*

    turn = { watch = true, refresh_on_end = true }

`watch` watches herdr agents for the last-turn baseline (|gh-review-turn|).
`refresh_on_end` refreshes an open last-turn review when the turn ends.

STACK AND LAYOUT ~
                                                        *gh-review-stack-opts*

    stack = {
      notes = true,            stack marks as virtual text in the diff
      data_edges = true,       ◆ keys passed between changed functions
      tests = false,           walk callers in test files too
      max_depth = 12,          caller levels walked
      max_frames = 400,        functions visited before giving up
      max_context_hops = 3,    unchanged functions climbed above changes
    },
    pr_drafts = true,          keep PR comments local (|gh-review-drafts|)
    diff_view = "split",       or "unified" (|gh-review-unified|)
    diff_inline = "word",      mark changed words in a line; "char" or "off".
                               Side by side this sets 'diffopt' inline:word
                               (Neovim 0.12+) while a review diff is open.
    files_position = "bottom", or "left"
    files_size = { bottom = 12, left = 50 },

12. Local Scopes                                          *gh-review-scopes*

A local scope reviews the working tree against a git base, with no PR and no
`gh`.  The head (right) pane is always the real file, so LSP works there.
Untracked files are included; the plugin snapshots the working tree through
a private copy of the index and never touches the real one.

    branch       The working tree against its merge base with {base}
                 (default: origin's default branch, else main or master).
    uncommitted  The working tree against HEAD.
    turn         The working tree against the last-turn baseline.

Comments are saved per branch in `<git-common-dir>/gh-review/<branch>.json`.
Right-side comments show in every local scope; left-side ones only against
the base they were made on.  A comment shows as pending (`CP`) until sent.
`:GHReviewDiscard` deletes unsent comments.

SENDING TO AN AGENT ~
                                                            *gh-review-agent*

|:GHReviewSend| pastes the comments, as one bracketed paste and unsubmitted,
into the first destination that works:

1. herdr: an agent in this herdr workspace other than Neovim's own pane, one
   in this repository first.  With several, |vim.ui.select()| asks, and the
   choice is remembered.  An agent at a permission prompt is skipped: the
   prompt would swallow the paste.
2. reviewr.nvim's transport, if installed: Neovim terminals, tmux, Rex,
   WezTerm.
3. The clipboard.

LAST TURN ~
                                                             *gh-review-turn*

Inside herdr, the plugin polls `herdr agent list` while Neovim runs.  When
the agents in this worktree go from idle to working, it snapshots the working
tree to `refs/worktree/gh-review/turn-base`.  Without herdr, the baseline is
the newest of that ref, herdr-reviewr's `refs/worktree/reviewr/turn-base`,
reviewr.nvim's `refs/reviewr/<worktree>/turn`, or a |:GHReviewTurn| mark.

13. Stack View                                             *gh-review-stack*

`s` in the files list shows the change as call stacks: one per entry point,
from the entry down to the changed functions, built from the diff and the
code in the background.  Rows read: >

    ▾ Chronos.Minute.Worker.CBB.handle_info/2  (+4 more entries)
      ~ Data.Action.GameStatus.Runner.run/1  runner.ex:20
        ⇢ Data.Action.GameStatus.Runner.process_game/1  runner.ex:40
<
    +  new function           ~  changed           -  removed
    ⇢  called asynchronously: :timer.apply_after, apply/3, or a
       {Module, :fun, args} tuple (RPC casts, scheduled jobs)
    ⇉  called through a variable: a behaviour's implementation ("via
       Tool"), or a module the calling file names as a value
    ↪  drawn above; <CR> jumps there
    ⚠  N other entry points reach this function: existing callers of
       code the change modified (only the frame where they cross in)
    ◆  a string key written by one changed function and read by
       another in another file (heuristic, added lines only)

Entry points whose call chains converge on the same function fold into one
line.  The largest groups form the change itself; smaller ones that mostly
reach the same code are listed under "Other entry points into changed code".

`gS` in the diff goes the other way: from the function under the cursor to
its row in the stack view (a removed one from the base side), opening the
list and building the view first when needed, and unfolding what hides it.

<CR> opens any function: one in a changed file as a diff at the function, a
removed one on the base side of its diff, and one in an unchanged file (a
caller on the way to the change) as the plain file at that line.  In the diff, `]s` and `[s` step
through the changed functions in stack order, and the same marks show as
virtual text (|gh-review-stack-opts| `notes`).

How it is built: changed functions come from parsing each changed file at
its base and head and comparing each function's own text.  Callers are
found with `rg` (files containing both the function name and the last
segment of its module), parsed with tree-sitter, and matched by module,
name, and arity, following aliases, imports, pipes, and captures.  The climb
stops at functions nobody calls, after `max_context_hops` unchanged
functions, or at the depth and frame limits ("↑ more callers").

Needs the head checked out (local scopes, or a PR with a checkout).
Languages: Elixir (the `elixir` tree-sitter parser), and basic Lua: required
modules and the file's returned table, but not functions passed through
tables (keymaps, callbacks).  Files in other languages are listed under
"Other changed files".

14. Unified View                                         *gh-review-unified*

`gu` in the diff or the files list switches between side-by-side and
unified, keeping the file and line.  `diff_view = "unified"` makes unified
the default.

The unified view is one window on the head file itself: LSP, go-to-
definition and editing work as usual.  Added and changed lines are
highlighted (DiffAdd, with the changed characters in DiffText), removed
lines are drawn as virtual lines (DiffDelete) above where they were, and
unchanged stretches fold with three lines of context.  `]c` and `[c` jump
between changes.  On added lines the cursor line is drawn with
`GHReviewUnifiedCursorLine` (default: DiffAdd lifted towards the text
colour, recomputed on |ColorScheme|), since the added-line background would
otherwise hide 'cursorline'.

The base file is loaded but not shown.  `gc` on a line with removed lines
drawn above it asks whether to comment on the line or on the removed lines;
base-side threads show on the head line their code maps to, marked
"(base)".
